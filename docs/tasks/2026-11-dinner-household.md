# Задача: «Приготовить ужин» — домочадцы, кухня, продукты, подбор блюд

Дата: 2026-11-10 · Клиент: Android (`feature/dinner`, этап 1 уже сделан локально)

## Контекст

Приложение уходит от «свайпов ради свайпов» к сценарию **«Что едим?» → «Приготовить ужин»**:
пользователь отмечает, кто сегодня ужинает, какая есть техника, готовим ли из того, что дома,
и получает блюда, которые **подходят всем за столом**.

Сейчас на Android всё это хранится только на устройстве, а подбор идёт по закэшированной
ленте с упрощёнными правилами. Нужно:

1. хранить данные о домочадцах, технике и продуктах **на сервере**;
2. перенести подбор блюд на сервер — там уже есть проверенные правила фильтрации ленты
   (`recommendation/ranking.ts`). На клиенте нашлась ошибка как раз из-за дублирования правил:
   диеты `LACTOSE_FREE` / `GLUTEN_FREE` клиент проверял как «у блюда есть метка», а это
   «у блюда нет молока/глютена» (см. `DIET_RULES`).

## Что уже есть и переиспользуем

- Ингредиенты у рецептов: `Ingredient`, `FoodIngredient`, и они уже отдаются в `FoodView.ingredients`.
- Признаки блюд для медицинских ограничений: `features.lowCalorie / lowFat / lowCarb / spicy /
  verySpicy / highSodium / highSugar`, плюс КБЖУ в `FoodNutrition`.
- Жёсткие фильтры и скоринг ленты: `buildHardFilters`, `DIET_RULES`, `scoreCandidate`.

## Требования

### 1. Профиль: пол и рекомендации врача

`User` получает `sex` (`MALE | FEMALE | null`) и `medicalRestrictions` (список из enum ниже).
Редактируются через существующий `PATCH /users/me`, отдаются в `GET /users/me`.

Сам пользователь — это «я» за столом: его аллергии/диеты/предпочтения уже живут в профиле,
поэтому отдельной записи «я» среди домочадцев **нет**.

`MedicalRestriction`: `LOW_CALORIE, LOW_FAT, LOW_CARB, NO_SPICY, LOW_SALT, LOW_SUGAR`.

### 2. Домочадцы (eaters)

Люди, для которых пользователь готовит. Не аккаунты — их никто не приглашает.

Поля: `id` (UUID, **генерирует клиент** — нужно для офлайн-создания), `name` (1..50),
`sex?`, `age?` (0..150), `likes[]` (коды кухонь/меток, мягкий сигнал), `avoid[]` (что не ест —
жёсткое исключение для ужина), `allergens[]` (коды аллергенов), `diets[]` (коды каталога диет),
`medicalRestrictions[]`. Не больше 20 домочадцев на аккаунт.

| Метод | Путь | Смысл |
|---|---|---|
| GET | `/users/me/household/eaters` | список, в порядке добавления |
| PUT | `/users/me/household/eaters/:eaterId` | создать или заменить целиком (идемпотентно) |
| DELETE | `/users/me/household/eaters/:eaterId` | удалить (идемпотентно) |

Чужой `eaterId` → 404 (не раскрываем, что такой id существует у другого пользователя).

### 3. Кухонная техника пользователя

| Метод | Путь | Смысл |
|---|---|---|
| GET | `/users/me/kitchen` | `{ appliances: string[] \| null }` — `null` = ещё не спрашивали |
| PUT | `/users/me/kitchen` | `{ appliances: [...] }` — заменить целиком; `[]` = «ничего не отмечено» |

`KitchenAppliance`: `STOVE, OVEN, AIR_FRYER, MICROWAVE, GRILL, MULTICOOKER, BLENDER`.

### 4. Продукты дома и каталог ингредиентов

| Метод | Путь | Смысл |
|---|---|---|
| GET | `/ingredients?search=&lang=` | поиск по каталогу для пользователя (до 50 шт.) |
| GET | `/users/me/pantry?lang=` | что есть дома: `{ items: [{ ingredientId, name }] }` |
| PUT | `/users/me/pantry` | `{ ingredientIds: [...] }` — заменить целиком; неизвестный id → 400 |

### 5. Техника, нужная для блюда

Новая таблица меток `FoodAppliances` (одна строка на блюдо, boolean-колонка на каждый прибор),
по образцу `FoodFeatures`. Отдаётся в `FoodView.tags.appliances` (коды `OVEN`, `AIR_FRYER`, …),
редактируется в админке в форме рецепта. Нет строки = блюду не нужна особая техника.

### 6. Подбор ужина

`GET /dinner/suggestions?eaterIds=&includeSelf=&source=&maxMissing=&limit=&lang=`

- `eaterIds` — домочадцы через запятую (можно пусто); `includeSelf` (по умолчанию `true`) — ест ли
  сам пользователь. Хотя бы один едок обязателен.
- `source` — `ANY` (по умолчанию) или `AT_HOME`.
- `maxMissing` (по умолчанию 2, 0..10) — для `AT_HOME`: сколько ингредиентов можно докупить
  (соль/вода/масло обычно не заносят в «продукты дома»).
- `limit` 1..50, по умолчанию 20. Без курсора — это короткий список, а не лента.

Ответ: `{ suggestions: [{ food: FoodView, missingIngredients: [{ ingredientId, name, amount, unit }] }] }`.
`missingIngredients` считается всегда, если у пользователя заполнены продукты дома, — для `ANY`
это готовый список покупок.

**Правила — блюдо должно подходить каждому едоку:**

| Источник | Правило |
|---|---|
| Аллергены, исключения, диеты | ровно как в ленте: `buildHardFilters` по каждому едоку, всё через AND |
| `avoid` / исключения про вкус (напр. «острое») | для ужина — **исключение**, а не понижение (в ленте понижение) |
| `LOW_CALORIE` | `features.lowCalorie` или калорий на порцию ≤ 500 |
| `LOW_FAT` | `features.lowFat` или жиров на порцию ≤ 15 г |
| `LOW_CARB` | `features.lowCarb` или `diets.keto` или углеводов ≤ 20 г |
| `NO_SPICY` | нет `features.spicy` и `features.verySpicy` |
| `LOW_SALT` | нет `features.highSodium` |
| `LOW_SUGAR` | нет `features.highSugar` |
| Техника (если пользователь её указал) | блюдо не требует техники, которой нет |
| `AT_HOME` | у блюда есть ингредиенты, и не хватает не больше `maxMissing` |
| История | блюда с DISLIKE пользователя не предлагаем |

Сортировка: сначала меньше недостающих ингредиентов (для `AT_HOME`), затем скоринг ленты
(вкус пользователя + `likes` всех едоков как заявленные предпочтения), затем новизна.

## Вне скоупа

- «Заказать еду» и «Поесть в городе».
- Нормы калорий по полу/возрасту/весу (нужны вес, рост и цель — отдельная задача).
- Количества продуктов дома (пока только «есть / нет»).

## Критерии приёмки
